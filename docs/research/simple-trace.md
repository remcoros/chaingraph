# Small output trace: semantics and limits

Reviewed 2026-09-09. This experiment follows one explicitly chosen output branch per action. It uses existing browser transaction contracts and network-scoped read-only RPC helpers. No external implementation was copied; the new application code is MIT-compatible.

- [Bitcoin transaction reference, outpoints and inputs](https://developer.bitcoin.org/reference/transactions.html#outpoint-the-specific-part-of-a-specific-output): an input identifies one previous transaction ID and output index. This supports exact creating/spending links. Transaction serialization contains no authoritative mapping from an individual input's satoshis to individual new outputs. Continuing through a transaction remains a user branch choice.
- [BIP78, PayJoin](https://bips.dev/78/): sender and receiver can contribute inputs, defeating common-input ownership assumptions. Multiple unequal outputs do not rule out collaboration. Trace explicitly requires a branch choice and never automatically selects a largest output or claims ownership.
- [Bitcoin Core 30.0, gettxout](https://bitcoincore.org/en/doc/30.0.0/rpc/blockchain/gettxout/): a positive result observes an unspent output at a particular node and time. Including mempool excludes outputs spent in that node's mempool. A null result or an empty bounded history search is not interpreted as proof of spending or of being unspent. Saved spending transactions are observations, potentially stale or competing.

Two modest structural hints are offered: one spendable output suggests a sole-output continuation; multiple inputs feeding one spendable output are consistent with consolidation. Neither establishes the same owner or allocates satoshis. Multiple inputs with equal output values trigger an ambiguity explanation, not a CoinJoin detector. Unequal outputs can still participate in collaborative transactions, including PayJoin and WabiSabi, so all continuations require explicit choice. Coinbase has no previous outpoint.

Backward lookup loads at most the chosen creating transaction. Forward lookup first uses loaded exact spends; otherwise it checks the selected output's current UTXO observation and at most one script history, considering only its first 12 distinct candidate transactions. The existing history helper rejects more than 10,000 entries. Failed candidate downloads and the number of unexamined entries remain visible. A 15-second action timeout and cancellation prevent unfinished results from merging. There is no automatic pagination, branch fan-out or recursive chain scan. A missing spender beyond the bound remains unknown. The session trail retains the latest 40 selections and is not a persisted evidentiary path.

Domain fixtures cover exact outpoints, wrong-index rejection, explicit scope, both hints, equal-output and PayJoin ambiguity, network routing, unspent versus absent, the candidate bound, partial failures, and cancellation after an upstream resolves. Real example snapshots are useful shape observations, not attributed wallet ownership or fresh network status.
